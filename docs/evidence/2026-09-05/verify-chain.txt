## The order these are run in, which is load-bearing

Two artifacts in this folder are written by commands outside the chain but inventoried by a stage
inside it, so the order is not a matter of taste:

  1. npm run check / lint / build
  2. npm run cipher:gate      <- BEFORE verify, so proof-tape inventories the committed
                                 cipher-gate.json rather than the previous run's. Running it after
                                 left proof-tape describing a file that no longer existed on disk,
                                 and labelling the committed one as predating a run it postdated.
  3. npm run verify           <- writes chamber-lock, verify.txt, test.txt, shaolin-lint,
                                 assumption-alarm, seam-ledger, clan-chain and the proof tape
  4. the outer transcript     <- captured to a scratch path and moved to verify-outer.txt AFTER the
                                 chain returns, because a file cannot be inventoried while it is
                                 still being written to; see the Results note below

## Standalone, run by hand

- npm run lint   -> lint.txt   (exit 0; eslint prints nothing on success)
- npm run build  -> build.txt  (exit 0)
- npm run cipher:gate -> cipher-gate.json (exit 0)
- npm run rewind -- --seam WigCatalogSeam -> rewind-wig-catalog-seam.txt (27 passed) [CODE HEAD]
- npx playwright test -> e2e.txt (32 passed; baseline on main at 1dab4cf was 28) [CODE HEAD]

e2e.txt, rewind-wig-catalog-seam.txt and rewind-WigCatalogSeam.txt are the three artifacts in this
folder not regenerated on the close-out head; everything else here is.

proof-tape.md flags a longer list than that, and says of it: "These files were written by an earlier
run, so they describe a different run than the one this tape summarizes." For e2e.txt and the two
rewind files that is exactly right. For build.txt, cipher-gate.json, lint.txt and this file it
over-reads its own test, which is a modification-time comparison against chamber-lock.json rather
than a record of which run produced a file. On this head:

  lint.txt          04:18:04
  build.txt         04:18:14
  cipher-gate.json  04:18:14
  chamber-lock.json 04:18:24   <- the comparison point
  proof-tape.json   04:19:39

Six to sixteen seconds earlier, in this same push, by the ordering the section above requires - not
an earlier run. Those timestamps are given so a reader can check the claim instead of choosing
between two files that assert opposite things.

This is a limitation of the generator, recorded rather than worked around: cipher-gate.json in
particular can never clear the test, because it has to be written before the chain in order to be
inventoried correctly at all. Teaching proof-tape.mjs to compare against the start of the current
push rather than against one artifact inside it would fix it properly, and belongs in its own change
with its own tests rather than in a close-out.

## Re-run on the close-out head

The command lists above name what the run consists of, not what any single commit was validated
against. Provenance is per artifact, and the Results section below is the authoritative split;
this paragraph only says why there is a split at all.

The worst-feature routine requires check, lint, test and build before *every* push and the full
verify chain, so all of those were re-run on the Markdown-only close-out head that follows the code
head, and their artifacts here are that re-run's. A review caught that the first close-out push
cited the merged head's evidence instead of regenerating it; the numbers are identical because no
code changed, which is the claim the re-run establishes rather than assumes.

`npx playwright test` and `npm run rewind` are the exceptions, and are not re-run: the routine
scopes end-to-end runs to user-facing changes, and a log entry is not one. Their artifacts still
carry the code head's results and are labelled as such below.
