## The order these are run in, which is load-bearing

Two artifacts in this folder are written by commands outside the chain but inventoried by a stage
inside it, so the order is not a matter of taste. It is stated in docs/evidence/README.md and
followed here:

  1. npm run check / lint / build
  2. npm run cipher:gate      <- BEFORE verify, so proof-tape inventories the committed
                                 cipher-gate.json rather than the previous run's.
  3. npm run verify           <- writes chamber-lock, verify.txt, test.txt, shaolin-lint,
                                 assumption-alarm, seam-ledger, clan-chain and the proof tape
  4. the outer transcript     <- captured to a scratch path and moved to verify-outer.txt AFTER the
                                 chain returns, because a file cannot be inventoried while it is
                                 still being written to; see the Results note below

## Standalone, run by hand

- npm run lint   -> lint.txt   (exit 0; eslint prints nothing on success)
- npm run build  -> build.txt  (exit 0)
- npm run cipher:gate -> cipher-gate.json (exit 0)

                 -> rewind-CreationStoreSeam-self-contained.txt
- npx playwright test -> e2e.txt
- node probes/browser-seams.probe.mjs -> probe-browser-seams.txt, and the fixture it rewrites

Every one of these was re-run on this head, and so was every artifact the chain writes. The
exception, stated rather than glossed: the `rewind-*.txt` files naming any seam OTHER than
`CreationStoreSeam (self-contained)` are an earlier run's, and are left that way deliberately. This
change touches one seam; those files describe seams it does not touch, and re-running them would
produce identical output while implying a scope this change does not have. The rule, rather than a
count that goes stale: a rewind artifact here is current if and only if its name is the seam in the
Cipher Gate entry. Which files that leaves is answerable from the repository —

  git diff --name-only <base>..HEAD -- 'docs/evidence/2026-09-05/rewind-*'

— rather than from a number typed into this file.

## Why proof-tape.md flags files this file says are current

proof-tape.md lists `build.txt`, `cipher-gate.json`, `e2e.txt`, `lint.txt`, every `rewind-*.txt`,
`verify-chain.txt` and `verify-outer.txt` as "older than this run's chamber-lock.json", and says of
them: "These files were written by an earlier run."

For the other seams' rewinds that is exactly right — see the paragraph above. For the rest it
over-reads its own test, which is a modification-time comparison against one artifact inside the
chain rather than a record of which run produced a file. Every one of them is written *before* the
chain, because the capture order requires it: the chain inventories them, and a file cannot be
inventoried before it exists. `cipher-gate.json` in particular can never clear the test, by
construction. `verify-outer.txt` is the mirror image — written *after* the chain, for the reason
under Results — and is flagged for the opposite reason.

The stamps written INTO the artifacts by the tools that produce them settle the ordering, and
survive a clone, a checkout and a squash in a way a file's modification time does not:

  grep -h '"generatedAt"' docs/evidence/2026-09-05/{cipher-gate.json,chamber-lock.json,proof-tape.json}

cipher-gate's precedes chamber-lock's, which precedes the tape's, which is the ordering the section
above requires. `lint.txt`, `build.txt` and `e2e.txt` carry no such stamp; nothing here claims a
measured gap for them, only that the sequence above put them in this push.

This is a limitation of the generator, recorded rather than worked around. Teaching proof-tape.mjs
to compare against the start of the current push rather than against one artifact inside it would
fix it properly, and belongs in its own change with its own tests.

## What `npx playwright test` does and does not report here

The mandated command FAILS in this container, and not because of the code. The image ships Chromium
build 1194 while `@playwright/test` pins 1208, so every test errors before its body runs, at browser
launch. `playwright install` is not available in this environment.

e2e.txt therefore carries two rows, and both are true:

- `npx playwright test` (the mandated command, unmodified): fails at launch, 0 tests run.
- The same suite against the browser the container actually has, via a scratch config that sets
  `launchOptions.executablePath` to /opt/pw-browsers/chromium: 38 passed.

The scratch config is not committed and is not part of the suite. It is excluded through
.git/info/exclude rather than .gitignore, so the exclusion is local to the machine that needs it and
no repository file claims a harness that does not ship. An earlier run of this routine let a
root-level copy of that config into a commit through `git add -A`, while its own log said the file
was never committed; that is why the exclusion is now mechanical rather than remembered.

## The probe, and why it is in this folder at all

`src/lib/seams/creation-store-seam/probe.ts` is a delegation note: this seam is probed by
`probes/browser-seams.probe.mjs`, which writes the fixture's inputs into a real browser's
localStorage and reads them back out. The contract change added `styleSelection` and the fixture's
INPUTS were updated to carry it — but the probe had not been re-run since, so the outputs beside
those inputs were hand-maintained rather than captured. Every schema, fixture and mock test in this
change reads those outputs, so not one of them could have told the difference. A review caught it.

Re-run on this head, and the capture found a divergence: the committed `output.getCreation` claimed
a record read back out of localStorage carries no `studioText`, while the record written into it
does. Browser storage keeps it. The style-bearing creation and draft do round-trip intact, which is
what the probe was asked to establish, but the point stands either way — the outputs were a hand-kept
copy of what a browser was assumed to return.

The transcript is probe-browser-seams.txt, including why the mandated command cannot launch a
browser here (the same Chromium 1194/1208 mismatch as the e2e suite, handled the same way). The
seam's contract test now pins the read-back outputs against the inputs, so a future hand-edit that
drops a field on the way out is red rather than invisible.

## The Cipher Gate entry, and what it claims

- DECISIONS.md carries a Cipher Gate entry dated 2026-09-05 for CreationStoreSeam, and this time it
  is a real seam change rather than a doubt resolved in favour of one: `CreationRecordSchema` and
  `DraftRecordSchema` each gain an optional `styleSelection`, and the seam gains the `validators.ts`
  artifact it was missing.
- The field is optional, and that is load-bearing rather than tidy. The production adapter parses
  every record out of localStorage through these schemas, so a required field would have failed
  validation on every record already in a reader's browser and emptied their vault on upgrade. The
  contract test parses a record with the key deleted, and making the field required turns ten vault
  tests red — measured, not asserted.
- chamber-lock.json is the artifact-presence gate for the seam's six files; rewind is its contract
  verification. Both are on this head.

## What this evidence does not prove

- The provenance guards in this change are invisible from the outside — a green suite cannot tell a
  page filed under the style that made it from a page filed under the controls that happen to be up.
  Each guard was confirmed by breaking it and watching a named test fail. Those mutation runs are
  recorded in WORST_TO_BEST_LOG.md under Run 7, not in this folder.
- Nothing here exercises the real xAI provider. Every generation in the unit suite and the
  end-to-end suite is a stubbed fetch, so what is proved is what the studio does with a response,
  not what a provider returns.
- SonarCloud's duplication gate reports a percentage and no location and cannot be run locally; the
  network policy returns 403 for sonarcloud.io. Its result is read from the pull request's check
  run, not from this folder.
