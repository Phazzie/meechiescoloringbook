## What the e2e suite proves that the unit tests cannot

Three of this change's guards are only observable in a browser, and each was confirmed by deleting
the guard and watching the test fail rather than by reading the code. This said "two" for most of
this run and omitted the third, which is a coverage claim a later audit would have read as complete:

  - The `{#key config.slug}` in src/routes/m/[mode]/+page.svelte. SvelteKit reuses one component
    instance across parameter changes on the same route, so without the key the previous mode's
    verdict survives into the next mode. The first version of this test navigated with `page.goto`,
    which builds a new document, and so passed with the key deleted — it proved nothing. It now
    walks an in-app link, marks the document, and asserts the mark survives the click, so it fails
    if the navigation ever stops being client-side.
  - The 404 for an unknown slug, which is a response status and not a rendered value.
  - The 32px horizontal overflow at a 390px viewport. `document.documentElement.scrollWidth`
    against `clientWidth` is a layout measurement, and jsdom does no layout, so no unit test can
    make this assertion at all. Removing the `overflow-x: clip` fails with
    "/m/who-fucked-up pans sideways by 32px".

  The dedication-split test is deliberately **not** in this list. It is about component state after
  a second verdict, which a component test with a DOM could assert; it runs in the e2e suite because
  that is where the verdict flow is already stubbed, not because a browser is required for it.
