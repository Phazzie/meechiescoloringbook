## Codex P1 on 742d146 — a concrete collision, accepted; the workflow demand, still declined

The earlier seam finding was refused as a general argument. This one is different: it names a
specific data-loss path, and it is right.

  `crypto.randomUUID` is gated on a secure context, so it is absent over plain HTTP and in some
  embedded webviews. The fallback was `creation-${Date.now()}`. `upsertRecord` in
  creation-store.adapter.ts filters by `existing.id !== record.id`, so two saves landing in the
  same millisecond — two tabs on one vault — silently dropped the first.

Worth stating plainly: this was not inherited. `session.adapter.ts` already mixes a random suffix
into its own clock-based fallback; the version written here omitted it, so it was weaker than the
precedent sitting next to it in the same repository.

Fixed with `newCreationId()`: `randomUUID` where available, then `crypto.getRandomValues` (which is
*not* secure-context gated, so it covers nearly everything `randomUUID` misses), then the session
adapter's clock-plus-random shape as a last resort.

`createdAtISO` now reads through `ClockSeam` rather than `new Date()`. The seam's own contract says
anything needing "now" must cross it. Its adapter already exists, so consuming it changes no
contract and touches no seam artifact — which is also why the second half of the finding, "complete
the required workflow", is still declined: nothing under contracts/, probes/, fixtures/,
src/lib/mocks/ or src/lib/adapters/ is modified by using an adapter that is already there.

### The test for this was wrong on the first attempt

The first version of the id test passed against the *broken* fallback. Two `withPage()` calls do
real async work between them, so the wall clock advanced past the collision window and the ids
differed for a reason that had nothing to do with the fix. Caught by mutating the fallback back and
seeing the test still pass — the third time in this run that a mutation has exposed a test proving
less than it claimed.

Rewritten with `Date.now` frozen, which is the only way to reach the case the finding describes.
Both branches are now pinned: restoring the clock-only fallback fails it, and disabling the
`getRandomValues` branch fails it and the branch's own test.

## SonarCloud Quality Gate FAILED on 564f24e — and it was mine

The first actual Quality Gate failure of this run, on a required condition: "C Security Rating on
New Code (required >= A)". The issue: "Pseudorandom number generators (PRNGs) should not be used in
security contexts", on the `Math.random()` in the previous commit's id fallback.

Every earlier SonarCloud finding here passed the gate and was fixed anyway. This one blocked, and
the cause was the fix for the round before it — introduced while removing a collision.

The rule's own framing is not quite right for this code: a vault record id is not a secret, and
nothing downstream treats it as unguessable. But the finding is still correct, for a better reason
than the rule states. `crypto.getRandomValues` — a cryptographic source — sits two lines above, and
the code reached past it for a pseudorandom one. Arguing "the id is not a secret" would have been
defending the habit rather than the code.

Fixed by removing the PRNG rather than by justifying it, and the replacement is strictly better:

  fallbackCounter += 1;
  return `creation-${Date.now()}-${fallbackCounter}`;

A monotonic counter cannot repeat within a document, which is exactly the guarantee `Date.now()`
alone was missing — so it answers the original collision finding more directly than `Math.random()`
did. And this branch needs a browser with no Web Crypto at all (`getRandomValues`, unlike
`randomUUID`, is not secure-context gated), so it is close to unreachable in practice.

The collision test still fails when the counter is removed and the clock-only id restored, so the
guarantee is pinned to behaviour rather than to the shape of the expression.

## Codex round on 4ef64dc — two findings, and the documentation one is the serious one

### The counter separated saves, not tabs

Correct, and it means the previous close-out overstated the fix. `fallbackCounter` is module-level,
so each document starts it at zero: two tabs saving in the same millisecond both emit
`creation-<ms>-1`, which is the two-tab collision the original P1 named.

Added `documentToken`, derived once per document from `performance.timeOrigin + performance.now()`
at sub-millisecond resolution. Two tabs almost never share one, and it is not a PRNG so the security
gate stays green. Stated in the code as a bound rather than a proof: two documents whose timeOrigin
matches to the microsecond, saving in the same millisecond, would still collide — and reaching this
branch at all needs a browser with no Web Crypto whatsoever.

### `/m/[mode]` is NOT orphaned, and this repo's own docs said it was

The more consequential finding, and it is a documentation defect rather than a code one.

`CLAUDE.md` described `/m/[mode]` as "Orphaned fourth implementation of the same modes. Linked from
nowhere, no generation. Delete candidate." Two of those three claims are false:

mounted by `src/routes/+page.svelte`, the home page. It also calls `/api/tools` and shows a verdict,

The claim originated in Run 2's log and was copied into `CLAUDE.md` by this run without checking it.
