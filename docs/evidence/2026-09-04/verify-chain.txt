## The ordering rule for the standalone artifacts, which still holds

`markArtifactsPredatingRun` in scripts/proof-tape.mjs takes its marker from the mtime of
chamber-lock.json, written at **stage 2** of the chain. Running lint, build and the e2e suite after
the chain makes them newer than that marker, but proof-tape.md was already rendered at stage 8 and
does not see them — so `npm run proof:tape` is invoked once more on its own afterwards. That order
was used here: chain, then the three standalone checks, then the tape.

## A note on the browser used for the e2e run

This container ships Chromium build 1194; the pinned @playwright/test resolves build 1208, and
downloading browsers is not available in this environment. The 1208 headless-shell path was
symlinked to the installed 1194 binary so the suite could run. `playwright.config.ts` is unchanged
and is not part of this diff — CI resolves its own browser in the normal way, so this affects the
local evidence run only and nothing about how the suite executes in CI.

## What the e2e suite proves that the unit tests cannot

Two of this change's guards are only observable in a browser, and both were confirmed by deleting
the guard and watching the test fail rather than by reading the code:

  - The `{#key config.slug}` in src/routes/m/[mode]/+page.svelte. SvelteKit reuses one component
    instance across parameter changes on the same route, so without the key the previous mode's
    verdict survives into the next mode. The first version of this test navigated with `page.goto`,
    which builds a new document, and so passed with the key deleted — it proved nothing. It now
    walks an in-app link, marks the document, and asserts the mark survives the click, so it fails
    if the navigation ever stops being client-side.
  - The 404 for an unknown slug, which is a response status and not a rendered value.

## Round 2 — the SonarCloud duplication gate, and what it was actually pointing at

SonarCloud's Quality Gate failed on the first head `75b0017`: **4.5% Duplication on New Code,
required <= 3%**. It is a measure rather than an issue, so it posts no check-run annotations and the
duplicated block has to be found by hand.

The first guess was wrong and is worth recording. The obvious suspect was the CSS in
`MeechieModePage.svelte`, which mirrors the three standalone mode routes — ten rule blocks are
byte-identical to `who-fucked-up/+page.svelte`. But SonarCloud's automatic analysis has no Svelte
parser: every SonarCloud finding in this repository's history is in a `.ts` file, and there is no
`sonar-project.properties` widening that. Refactoring the stylesheets would have been a large,
risky change to three working routes that fixed nothing.

The real duplication was twelve byte-identical lines of TypeScript between the new
`a focused mode page turns its verdict into a coloring page` test and the existing
`a page made on a mode route can be saved and found in the home vault` test — the same closing
sequence, down to the `'For the group chat'` literal, because the new test was written from the old
one. Extracted as `makePageAndKeepIt`, which both now call. That is the same fix, for the same
gate, that `makeToolkitPage` already represents in this file.

Measured rather than assumed afterwards: an 8-line n-gram scan across the changed `.ts` files
against the rest of `src/`, `tests/` and `contracts/` reports no remaining cross-file or internal
duplication in new code. The two internal repeats it still finds in `tests/e2e/smoke.spec.ts`
(lines 573 and 851) are in tests that predate this pull request, so they are not new code.
